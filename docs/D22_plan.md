# D22：解决链路 Intent 与既有 MCP 接入

日期：2026-10-17。

当前状态：Intent 修正已实现；MCP 的目录、调用范围与下载通道原则已确认。2026-10-17 用户进一步明确滚动探索与外层整理 Fact 的职责，下方旧固定链路须据此调整。外层整理能力原已通过 D5 ProcessRefinement 和 D8-2 HandoffContext 实现并接入；尚未完成的是 MCP 执行接入，以及将既有整理能力与本次正式 Fact 定义、写入时点和生命周期衔接，不能把本文件或新版本号视为已经实现。

## 已确认的 Intent 标准

外层根据任务目标、前置 Intent、执行完成后的有效 Fact、已审核推断、内层建议和未解决问题，生成下一 Turn 的不同大方向。方向指整体探索路线、核心假设或证据推导路径，不能仅按工具、URL、参数或措辞区分。Intent 是探索性的，不要求生成时即可判断成功，也不要求列完工具、完整 Plan 或未来执行顺序。兄弟候选从相同当前状态出发，不能互相充当尚未完成的前置步骤。

MCP 只是动作可选择的工具，不另设要求模型事先承诺完整工具链的“MCP Plan”。内层沿当前 Intent，依据最新证据滚动决定下一动作、MCP 与参数；允许根据结果改变局部做法。Plan 若保留，只表示当前可调整的执行安排，不能把预见全部步骤作为开始执行的前提。是否有意义由既有进展复盘判断，不以某次结果偏离预期自动判方向失败。

取消原 1–2 条硬限制，内层 next_intent_candidates 同步取消原 0–2 条硬限制。四五个有价值的方向可以接受，只有一个方向也不凑数；完整响应、上下文容量、已有预算与 Deadline 继续约束生成和执行。

新内部 22／公共 d8_v22／两角色提示 v17 启用；新工作台默认 22，旧运行按原声明和证据恢复。没有增加语义分类器，也没有根据字符串相似度拒绝模型方向。

tree_planning 的所有 pending/running Intent 都是必要上下文，按当前有效引用注入 history；active_intent_frontier 显式列出其 Intent、Turn、状态和引用。必要上下文放不下时沿原容量暂停，不静默遗漏活动候选。前置 Intent／支持 Fact 和内层建议继续走既有来源与外层接受边界。

Schema、业务解析、内层建议重载、树注册、规划证据重载及错误索引检查使用相同数量规则，避免只修改 Prompt 后仍在后续阶段被旧限制拒绝。

## 已确认的 MCP 范围

1. 新任务始终向模型提供 registry 中已启用 MCP 供选择；复用 MCPManager、注册表和已有 Sandbox 执行机制，不另建执行容器。
2. 工具选择不扩展任务目标授权，调用继续经过预算、执行与证据台账、外层 Fact 审核和未知结果不重放的边界。旧运行不追加工具授权。
3. 同一容器提供 /challenge、/work、/tools 兼容路径；运行中下载的附件允许留在 Sandbox 内，不能退化为只能使用初始附件。
4. Download 仅安装所需原生工具或固定版本 Python 包，不动态下载并注册 MCP Server。安装在本 TaskRun 专属 Sandbox 内，保留 SHA 校验和总 Deadline。
5. 工具源下载采用与题目目标流量分离的受控通道，限定本次明确选择的 HTTPS 工具 URL／固定版本包，不开放任意外网。

## 2026-10-17 已确认的 Fact 职责

工具返回只产生执行记录／Evidence，不自动产生 Fact，也不要求一调用、一 Plan 或一 Intent 对应一条 Fact。内层依据观察提出候选、理由和证据引用；外层读取所需真实证据后，负责挑选重要内容、去重、合并、精简并形成正式 Fact，或拒绝／指出不足。外层可以输出不同于内层候选原文的最终正文，不再只有对原文的接受／拒绝权。

本次定义的 verified Fact 表示外层已审核并接受的正式结论，不能继续等同于固定程序生成的大小／SHA／HTTP 模板观察。程序负责验证证据存在、来源归属、版本、完整性、审核绑定和提交一致性；它不依据工具成功、输出字符串或 Hash 自行决定语义结论正确，也不能用原机械正文覆盖外层的最终正文。

正式结论应有与其强度相符的证据。外层精简不得把推测改写成确定事实；仍待证实的假设保留推断标记及依据。正式 Fact 与原始证据分层保存：正文精炼，但每条保留所依据的候选、执行和证据版本，允许合并多来源。后续纠正继续追加版本、保留历史；未裁决冲突不能被摘要掩盖。

用户确认整理时点为：既有定期复盘、内层主动申请、Intent 结束交接。允许长任务增量保留重要发现，每次可以不新增 Fact；不能强迫每次 MCP 调用后写一条。拒绝 Fact 不直接中止探索，已知证据范围内继续任务；未知执行、坏证据和提交不确定仍沿恢复边界。

本条覆盖 D8 早期标准中“外层不能修改候选”“仅注册机械规则才能写 verified”“正式 Fact 正文固定由程序生成”等与本次定义冲突的新运行设计；历史运行及证据保持其原含义，不回写为本次语义。

## 已核实的实现差异

外层整理不是缺失功能：原流程图已规定外层提炼 Process_Fact；multi_turn_application 将 ProcessRefinement 默认绑定 outer_model，并在已提交复盘后按新增合格来源触发提炼。HandoffContext 的 handoff_summary 同样由外层整理轮摘要、全局摘要、引用顺序和未解决问题；已有运行保存了 origin=model_organized 的摘要。当前 Process_Fact、交接摘要与 verified ResultFact 分开保存，不能把单条 fact_review 的输出限制概括为“外层尚未实现整理”。后续优先复用这两套现有能力，明确正式 Fact 的输出及提交衔接，不另建重复整理流程。

现有 MCPManager 绑定 SandboxService；D8 当前使用 T6TaskRunSandbox／D8DockerWorkspace。旧 MCP 的目录和 /tools 安装目录也未装配到当前只读根配置。直接实例化 MCPManager 不能证明它已经绑定到当前 TaskRun 的同一容器。

当前 D8 Plan 仅支持固定摘要或一次 HTTP 请求，且每 Intent 最多两个 Plan。这些是旧切片的执行限制，不能成为探索性 Intent 的产品定义；接入需要支持滚动选择动作及连续工具调用，保留已有预算、步数复盘和 Deadline。

当前 fact_review 只接受 decision／reason，不能输出合并精简正文；ConclusionReview 将无注册断言的认可归为推断；complete_d3_plan 最后使用 source.fact_content() 固定模板，并将 Plan 完成与单一 Fact 绑定。此整组行为需要调整，不能仅修改 Prompt、把机械观察换名或让 MCP 输出直接进入 verified 集合。

## 设计原则：宽容与严格的边界

遵循"对 LLM 宽容，对系统严格；对语义宽容，对执行严格；对输入宽容，对输出边界严格"的指导思想：

### 对 LLM 宽容（Lenient toward the LLM）

1. **方向选择自由**：不限制 Intent 候选数量为固定 1-2 条；允许 0-5+ 条有意义的方向，不强制凑数。
2. **工具选择灵活**：内层可根据当前证据滚动选择 MCP 工具和参数，不要求事先承诺完整工具链。
3. **局部调整许可**：允许根据执行结果改变局部做法，Plan 可调整，不以偏离预期自动判方向失败。
4. **语义理解包容**：不引入字符串相似度拒绝或语义分类器；由外层根据证据判断方向价值，不在生成阶段预判。
5. **候选提出宽松**：内层可提出多条 Fact 候选，包含推测和假设；外层负责审核强度与证据匹配。

### 对系统严格（Strict about the system）

1. **容器隔离保证**：MCP 执行必须在当前 TaskRun 的 Sandbox 内，不能跨 TaskRun 共享状态或泄露附件。
2. **授权边界固定**：工具选择不扩展任务目标授权；所有调用经过预算、台账和证据审核。
3. **下载通道受控**：Download 仅安装明确选择的 HTTPS 工具 URL 或固定版本包，SHA 校验必须通过。
4. **证据可追溯性**：每条 verified Fact 保留候选来源、执行记录和证据版本；后续纠正追加版本不覆盖历史。
5. **恢复一致性**：旧运行按原声明和证据恢复，不追加工具授权，不用新语义回写历史。

### 对语义宽容（Lenient toward semantics）

1. **探索性定位**：Intent 是探索路线，不要求生成时即可判断成功，允许尝试后复盘价值。
2. **推断标记保留**：外层精简不得把推测改写成确定事实；仍待证实的假设保留推断标记及依据。
3. **合并来源灵活**：外层可输出不同于内层候选原文的最终正文，允许合并多来源、去重、精简。
4. **方向分歧接受**：兄弟候选代表不同探索路线，不因部分相同工具或目标域判为重复。

### 对执行严格（Strict about execution）

1. **步数与预算**：滚动执行受已有预算、步数复盘和 Deadline 约束，不能无限调用。
2. **证据强度要求**：正式结论应有与其强度相符的证据；未知执行、坏证据和提交不确定仍沿恢复边界。
3. **审核流程必经**：工具返回产生 Evidence，内层提出候选；外层读取真实证据后审核，程序验证证据存在、来源归属、完整性。
4. **状态转换确定**：Intent 状态（pending/running/completed/failed）转换经过明确触发点，不能静默遗漏活动候选。

### 对输入宽容（Lenient toward input）

1. **上下文注入弹性**：所有 pending/running Intent 都是必要上下文，按当前有效引用注入；放不下时暂停，不静默遗漏。
2. **前置依赖灵活**：前置 Intent、支持 Fact 和内层建议走既有来源与外层接受边界，不要求预先完整。
3. **MCP 工具发现**：新任务始终向模型提供 registry 中已启用 MCP 供选择，不限制工具集合大小。

### 对输出边界严格（Strict about output boundaries）

1. **Fact 提交时点**：整理时点为既有定期复盘、内层主动申请、Intent 结束交接；不强迫每次 MCP 调用后写一条。
2. **正式结论分层**：verified Fact 表示外层已审核的正式结论，与原始 Evidence 分层保存；正文精炼但保留证据引用。
3. **模板观察退役**：取消固定程序生成的大小/SHA/HTTP 模板观察自动成为 verified Fact；程序负责验证，不决定语义结论正确。
4. **拒绝不中止**：拒绝 Fact 候选不直接中止探索；已知证据范围内继续任务，由复盘判断方向价值。

## 实现路线图

### Phase 1：MCP 执行接入（优先级：高）

**目标**：将 MCPManager 正确绑定到当前 TaskRun 的 Sandbox，支持滚动工具调用。

**具体任务**：
1. 验证 MCPManager 与 T6TaskRunSandbox/D8DockerWorkspace 的绑定路径
2. 装配 MCP 目录和 /tools 安装目录到当前容器配置
3. 扩展 D8 Plan 执行器，支持连续工具调用而非仅一次 HTTP 请求
4. 移除"每 Intent 最多两个 Plan"的硬限制，改为预算和步数约束
5. 实现 Download 的 HTTPS 工具 URL 和固定版本包安装，附带 SHA 校验

**验收标准**：
- 内层可在单个 Intent 内连续调用不同 MCP 工具
- 所有工具执行在同一 Sandbox 内，附件可跨调用访问
- Download 拒绝非 HTTPS 或未明确选择的 URL
- 工具调用受预算、步数和 Deadline 约束，超限时正确暂停

### Phase 2：Fact 整理能力衔接（优先级：高）

**目标**：将既有 ProcessRefinement 和 HandoffContext 与新 Fact 定义、写入时点和生命周期对接。

**具体任务**：
1. 扩展 fact_review 输出 Schema，支持 refined_content（合并精简正文）和 merged_sources（多来源引用）
2. 修改 ConclusionReview，允许外层输出推断标记保留的假设类 Fact
3. 解除 complete_d3_plan 中 Plan 完成与单一 Fact 的强绑定
4. 实现 Fact 提交时点逻辑：定期复盘、内层申请、Intent 结束交接
5. 建立 verified Fact 与 Evidence 的分层存储结构，保留候选来源和证据版本

**验收标准**：
- 外层可输出不同于内层候选原文的最终 Fact，带推断标记
- 单个 Intent 可产生 0 或多条 Fact，不强制一一对应
- 每条 verified Fact 可追溯到多条候选和 Evidence
- 程序验证证据存在和完整性，但不覆盖外层的语义结论
- 拒绝 Fact 候选后，探索继续而非中止

### Phase 3：Intent 树上下文管理（优先级：中）

**目标**：确保所有活动 Intent 作为必要上下文注入，容量不足时正确暂停。

**具体任务**：
1. 实现 active_intent_frontier 的显式列出逻辑（Intent、Turn、状态、引用）
2. 按当前有效引用注入所有 pending/running Intent 到 history
3. 添加上下文容量检查，放不下时暂停并记录原因，不静默遗漏
4. 统一 Schema、业务解析、内层建议重载、树注册、规划证据重载及错误索引的数量规则

**验收标准**：
- tree_planning 中所有活动候选都出现在注入的 history 中
- 容量不足时，系统暂停并向用户报告哪些 Intent 未能注入
- 数量规则在 Prompt、Schema 和各解析阶段保持一致

### Phase 4：恢复与迁移策略（优先级：中）

**目标**：安全处理旧运行，不用新语义回写历史。

**具体任务**：
1. 为新版本标记 version=22 或 d8_v22，旧运行保留原版本号
2. 恢复旧运行时，按其原 Schema 解析 Intent 数量限制（0-2 条）
3. 旧运行不追加 MCP 工具授权，不将机械观察升级为新定义的 verified Fact
4. 历史 Process_Fact 和 handoff_summary 保持 origin=model_organized，不改写为新 Fact
5. 提供迁移脚本，可选地将旧运行的重要发现手动提升为新 Fact（需人工审核）

**验收标准**：
- 恢复旧运行后，其 Intent 候选数、Plan 限制和 Fact 语义与原运行一致
- 新运行使用新 Intent 标准和 MCP 工具，标记 version=22
- 混合工作台可同时运行新旧版本任务，互不干扰

### Phase 5：测试与监控（优先级：中低）

**目标**：建立端到端测试覆盖和运行时监控。

**具体任务**：
1. 编写 MCP 工具链调用的集成测试（模拟 Sandbox 环境）
2. 编写 Fact 整理流程的端到端测试（内层候选→外层审核→分层存储）
3. 编写 Intent 树上下文注入的容量边界测试
4. 添加运行时监控：MCP 调用频率、Fact 生成速率、上下文溢出频率
5. 建立 Dashboard，可视化当前活动 Intent 树和 Fact 演化历史

**验收标准**：
- 集成测试覆盖 MCP 工具选择、连续调用、Download、SHA 校验失败路径
- 端到端测试覆盖内层提出 5 条候选、外层合并为 2 条 Fact 的场景
- 容量边界测试确认 10 个并发 Intent 时正确暂停而非静默遗漏
- Dashboard 可实时查看任意 TaskRun 的 Intent 树和 Fact 演化

## 待解决问题

1. **MCP 工具注册表动态性**：当前设计假设 registry 在任务启动时固定；若需运行时发现新工具（如从题目描述中提取 API 规范），是否扩展 registry 更新机制？
2. **多 Intent 并发执行**：当前设计允许多个 pending Intent，但未明确是否支持多个 running Intent 并发执行（可能需要 Sandbox 资源隔离）。
3. **Fact 冲突裁决**：当内层提出相互矛盾的候选，外层如何明确标记冲突并决定裁决时点？当前"未裁决冲突不能被摘要掩盖"，但缺少冲突检测和裁决的具体流程。
4. **长任务增量保存**：既有定期复盘的触发条件未明确（时间间隔？步数？Token 消耗？）；内层主动申请的协议未定义（特殊标记？显式 API？）。
5. **工作台默认版本切换**：新工作台默认 22，旧运行按原声明恢复；是否需要用户可配置的版本选择开关？迁移窗口期的兼容策略？

## 成功标准

本次集成视为成功，当：

1. **功能完备性**：内层可在单个探索性 Intent 内滚动选择并连续调用 MCP 工具；外层可合并多来源、精简并输出带推断标记的 verified Fact。
2. **系统保证**：所有 MCP 执行在 TaskRun 专属 Sandbox 内；Download 仅安装受控 HTTPS 工具；证据链完整可追溯；旧运行按原语义恢复。
3. **边界清晰**：宽容与严格的边界在代码、Schema 和 Prompt 中保持一致；数量限制、授权范围和审核流程在各阶段同步调整。
4. **可观测性**：运行时可查询当前活动 Intent 树、Fact 演化历史和 MCP 调用台账；容量不足时明确报告未注入的上下文。
5. **向后兼容**：旧运行不因新版本部署而改变行为；迁移路径清晰且可选；混合工作台稳定运行。
